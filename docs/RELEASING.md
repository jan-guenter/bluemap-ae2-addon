## Version contract

- Development version: `0.1.0-alpha.1-SNAPSHOT`.
- First possible gated release: no earlier than complete M0-M5 acceptance,
  including S1 cable-bus structural-completeness visual acceptance;
  the version remains provisional until then.
- Release tag: exactly `v<addon_version>`.
- Any pull request that changes `addon_version` must also update the changelog,
  compatibility, provenance and relevant runtime evidence.
- Tags must identify a clean commit reachable from `main`.
- Release-candidate builds use exact Eclipse Temurin `21.0.12+8`. A moving
  Java 21 selector is not a promotion toolchain.
- Treat published Maven versions and release tags as immutable. Never reuse a
  version or move its tag; the repository controls below enforce that policy.

## Repository controls required before any future first tag

The workflow cannot grant itself repository-administration authority. Before
creating the first release tag, the owner must configure and independently
verify all of these GitHub settings:

- protect `main` with the required CI check and reviewed pull requests;
- add a tag ruleset for `v*` that restricts creation and blocks update and
  deletion outside the explicitly authorized release role; and
- enable GitHub Immutable Releases so a published Release and its tag/assets
  cannot later be changed.

Record the non-sensitive settings audit with the publication evidence. Missing
or disabled controls block the tag; documentation alone does not make a Git
reference or Release immutable.

## Release-candidate manifest

Every non-SNAPSHOT version requires
`release-candidates/<addon_version>.json`. This file is committed only after
the exact release-version CI outputs have passed isolated runtime and human
acceptance. It is a repository and Release evidence file, not an add-on
resource; neither the production nor sources JAR contains it.

The schema is deliberately closed. The root contains exactly
`schemaVersion`, `project`, `version`, `promotionJava`, `evidence`, and
`artifacts`. Version 1 requires:

- `schemaVersion` equal to `1`;
- project `io.github.jan-guenter:bluemap-ae2-addon` and the exact release
  version;
- promotion Java distribution `temurin` and version `21.0.12+8`;
- a bounded, non-sensitive opaque evidence ID plus its ISO `YYYY-MM-DD`
  acceptance date; and
- byte size and lowercase SHA-256 for `productionJar`, `sourcesJar`, `pom`,
  and `moduleMetadata`.

Each artifact record contains exactly `sizeBytes` and `sha256`. Do not put a
Git commit, paths, player identity, server address, world data, or log content
in this manifest. `verifyReleaseCandidate` checks the strict schema and all
four locally generated files. An extra field is an error rather than an
unreviewed extension point.

the production JAR rejects nested JARs, third-party classes/resources,
worlds, screenshots, client captures, Minecraft/NeoForge metadata and every
unlisted file.

## Two-pass release pull request

The digest gate intentionally makes release preparation a two-pass process:

1. change `addon_version` to the non-SNAPSHOT release version, add the dated
   changelog heading, and complete every source/evidence change;
2. push the pull request without a candidate manifest. CI validates and
   uploads the exact Temurin release-version outputs, then fails its final
   `verifyReleaseCandidate` step because acceptance is still missing;
3. download the four CI outputs, retain their sizes and SHA-256 values, and
   stage the exact production JAR through the enabled/stock/re-enabled,
   deterministic, concurrent and human visual gates;
4. after acceptance, add only
   `release-candidates/<addon_version>.json` with those four identities and a
   non-sensitive evidence ID/date; and
5. rerun CI. The rebuild must be byte-identical to the accepted files before
   the pull request can merge.

If any source, packaged metadata, legal notice, build logic, or promotion
toolchain changes after candidate capture, discard the manifest and repeat
the cycle. A documentation-only change is not automatically harmless: rely
on the four digest checks, not an assumption. After merge, require successful
`main` CI on the exact commit before tagging it.

## GitHub release workflow

Only after the owner accepts the complete M0-M5 evidence and separately
authorizes publication:

1. change the version from SNAPSHOT to the exact release version through a
   reviewed pull request;
2. complete the two-pass candidate capture and add a dated changelog heading;
3. merge only after candidate verification, then wait for successful `main`
   CI and create/push the exact release tag;
4. let `.github/workflows/release.yml` rebuild twice and verify the candidate
   before its first Release, attestation, or package write;
5. let it create a draft Release, attest both JARs, publish Maven coordinates
   once, then publish the Release as a prerelease; and
6. verify the public tag target, Release assets, `SHA256SUMS`, candidate
   manifest, attestations and GitHub Packages coordinates independently.

The Maven coordinate is:

```text
io.github.jan-guenter:bluemap-ae2-addon:<version>
```

The release workflow must never upload the AE2 input JAR, staging worlds,
screenshots, logs or credentials.

GitHub's public Maven registry still requires authentication to download a
package. Use a token with package-read access for independent Maven
verification; GitHub Release assets remain the normal unauthenticated
installation channel.

## Failure recovery after publication starts

The workflow keeps the GitHub Release in draft form until Maven publication
succeeds. All release tags share one concurrency group because every version
updates the same artifact-root `maven-metadata.xml`. A rerun probes the four
primary Maven files, their required SHA-1/MD5 sidecars, and the artifact-root
metadata plus its sidecars before publishing:

- if the version payloads and sidecars are all absent and root metadata does
  not list the version, it permits the one publication attempt;
- if all payloads are byte-identical to the accepted candidate, all sidecars
  validate, and root metadata lists the version exactly once, it skips the
  Maven task and continues the retained draft; and
- if the transaction is partial, metadata is inconsistent, or any byte or
  checksum differs, it fails closed.

Before attestation or publication, the draft must contain exactly the six
allowlisted assets and every downloaded asset must match the local release
bundle byte-for-byte. A stale extra asset is a hard failure and cannot become
public through a retry.

Therefore a transient failure after Maven success can be resumed by rerunning
the same immutable tag workflow; it will not attempt to republish the version.
Do not delete a successful package, move the tag, or use `--clobber` against
Maven. If the workflow reports partial or mismatched package state, retain the
draft and logs, keep the bad state visible, correct the source, and use a new
version. If automated continuation itself is unavailable, verify all four
package files, every required SHA-1/MD5 sidecar, the artifact-root
`maven-metadata.xml` and its sidecars, and the exact six draft assets manually
before publishing that existing draft with the same prerelease/latest
classification.
